# Architecture and contributor guide

[Back to README](../README.md)

flow has two execution paths: drafting a feature document through a local provider
CLI, and implementing an approved document through T3. Both save durable state in
SQLite, but only the second path creates worktrees and publishes draft PRs.

## Where to start

Read [main.ts](../src/main.ts) for the available commands, then
[cli/actions.ts](../src/cli/actions.ts) for dispatch. Command handlers live in
[cli/commands/](../src/cli/commands/); they own terminal input/output and connect
configuration, storage, providers, and workflow operations.

For drafting, follow [cli/commands/new.ts](../src/cli/commands/new.ts) into
[features/draft-feature.ts](../src/features/draft-feature.ts). For implementation,
follow [cli/commands/run.ts](../src/cli/commands/run.ts) into
[workflow/start-job.ts](../src/workflow/start-job.ts) and
[workflow/runner.ts](../src/workflow/runner.ts).

## Module ownership

- `src/cli/`: terminal prompts, configuration and feature selection, recovery
  choices, command handlers, and output formatting. `context.ts` opens repository
  state and releases the process claim; `output.ts` contains pure formatters.
- `src/features/`: Markdown parsing and validation (`documents.ts`), durable draft
  requests (`draft-feature.ts`), and Codex/Claude invocation and output parsing
  (`draft-provider.ts`). The interactive wizard lives in `cli/new-feature-wizard.ts`.
- `src/workflow/`: job types, prerequisite checks, job creation, agent prompts,
  launch reconciliation and workspace checks, evidence checking, validation
  predicates, PR publication, and the workflow state machine. `runner.ts` keeps
  stage transitions and their persistence order together.
- `src/t3/`: the T3 executor and the wire schemas it consumes.
- `src/executor.ts`: executor contract and structured agent result schemas.
- `src/git.ts`: Git/worktree operations and GitHub CLI queries. Its `publish`
  method delegates publication orchestration to `workflow/publication.ts` while
  retaining the injectable adapter used by workflow tests.
- `src/state-store.ts`: SQLite persistence and repository process claims. Workflow
  state types belong to `workflow/job.ts`, independently of storage.
- `src/config.ts`, `src/init.ts`, `src/process.ts`: configuration loading,
  repository initialization, and subprocess execution respectively.
- `src/roadmap.ts`: versioned roadmap data consumed by status and JSON export.

Keep helpers next to their owning responsibility. Shared validation predicates
live in `workflow/validation.ts`; prompt construction lives in
`workflow/prompts.ts`. Avoid a catch-all helpers module.

## Repository files versus runtime files

`src/` contains implementation, `test/` contains automated tests, `docs/` contains
reference material, and `examples/` contains sample feature documents. `dist/` is
generated by the build and is ignored by Git.

When flow initializes a target repository, it creates `features/` and
`flow.config.json`. That repository's `.flow/state.sqlite` holds approvals, draft
attempts, jobs, and process claims; `.flow/` is ignored. These runtime files do not
belong in flow's own source tree.

## Verification

From the flow repository, with Node 24 or later and pnpm 11.20.0:

```sh
pnpm install --frozen-lockfile
pnpm run check
pnpm test
pnpm run format:check
pnpm run build
node dist/main.js --help
```

Tests remain flat under `test/`, matching the `test/*.test.ts` script. Module tests
use descriptive filenames; `workflow.test.ts` exercises transitions and recovery
with fake execution. `workflow.integration.test.ts` combines real local Git and
worktrees with fake T3/GitHub; `publication.test.ts` uses a disposable local remote
and a fake GitHub CLI. Neither suite creates real GitHub PRs.

See [integration verification](integration-verification.md) for the limits of live
integration coverage.
