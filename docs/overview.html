What moves through the system?

Documents store intent. SQLite stores execution state. Git tree IDs connect review and validation to the exact candidate contents.

01

Draft and approve

User request→Local Codex / Claude CLI→Draft Markdown→Human approval
  • flow new preserves the request and validates generated Markdown.
  • flow ready records approval for the exact document bytes.
  • Open questions require explicit acknowledgment.
02

Freeze scope and launch

Approved document + config→Saved job snapshot→T3-owned worktree
  • flow checks the current approval hash and prerequisite PR states.
  • flow fetches the configured remote base branch.
  • T3 receives the approved scope, repository instructions, and validation expectations.
  • The job retains thread IDs, run IDs, branch, and workspace binding.
03

Review and revise

Diff + acceptance evidence→Fresh reviewer→Structured verdict
  • The reviewer receives the approved document and prior review history.
  • A new review thread binds explicitly to the implementation worktree.
  • Findings return to the implementation context for revision.
  • A passing result must have no findings or unmet acceptance criteria.
04

Validate and publish

Reviewed tree→Required checks→Commit + push→Draft PR
  • Validation results record the command, exit code, and candidate tree.
  • The PR description includes scope, acceptance evidence, review, and validation.
  • flow saves the PR URL and links it to the implementation thread.

Select a stage to inspect its input, required checks, and saved output. An agent's completed turn alone cannot advance the job.

01 · Scope and eligibility

preparing

Check approval and dependencies before implementation starts.

Required checks

  • The approval matches the current document.
  • Prerequisite PRs are confirmed merged.
  • Validation commands exist.
  • No other feature is executing.

Saved output

Job ID, approved snapshot and hash, configuration, base commit, and unique branch.

  1. Prepare: verify approval, dependencies, and the repository claim.
  2. Implement: collect acceptance evidence in the dedicated worktree.
  3. Review: require a fresh thread and a valid structured result.
  4. Revise: address findings, then request a fresh review.
  5. Validate: run required commands against the final tree.
  6. Publish: commit, push, and create or recover the draft PR.
  7. PR open: wait for external review and merge.
Revision loop: reviewing → changes required → revising → fresh reviewing. Default limit: two automatic revision rounds.
Changed candidate? A review or validation pass applies to a specific Git tree. Further changes require a fresh review and validation.

Dependency eligibility

Feature A: PR merged→Feature B: dependency satisfied
  • An open PR does not satisfy a dependency.
  • An unknown PR state blocks execution.
  • Other approval and execution checks still apply to Feature B.

Resume from recorded facts.

flow records operation intent before launch or publication. Recovery checks backend and Git state before it decides what to do next.

Durability

Keep progress across CLI exits

  • SQLite uses write-ahead logging and full synchronous writes.
  • A process claim prevents concurrent flow runners.
  • Claims from dead local processes can be reclaimed.
  • Worktrees and user files remain in place.
Control

Keep uncertain operations visible

  • Retain launch titles and thread/run IDs.
  • Mark validation commands that are in progress.
  • Check commits, remote branches, and existing PRs.
  • Ask for human input when the outcome is unknown.
A local drafting call stops or fails
  1. Use flow new --id <id> to collect saved successful output.
  2. If no successful result exists, confirm the local agent has stopped.
  3. Use flow new --id <id> --retry-draft to try again.
  4. Add --provider codex or --provider claude to change providers.

flow retains the input and attempt history. Drafting does not connect to T3.

A T3 launch response is missing
  1. flow searches for the saved unique thread title.
  2. If exactly one thread matches, flow adopts its handle.
  3. If the result is uncertain, inspect T3.
  4. Only after confirming no thread exists, use resume --retry-launch.
A review fails or the revision limit is reached
  1. Read the findings in the review thread.
  2. Resolve the issues in the implementation worktree.
  3. Use resume --recheck for a new independent review and validation.

This command does not reset the automatic revision limit.

Validation stops before flow records completion
  1. Confirm that its subprocesses have stopped.
  2. Use resume --retry-validation.
  3. Add --recheck if files changed.
A PR creation response is missing
  1. flow checks the branch and existing PRs.
  2. If a matching PR exists, flow records its URL.
  3. If none is visible, inspect GitHub before using resume --retry-publish.

flow does not force-push or silently overwrite a mismatched remote branch.

A thread asks a question, or a job must be cancelled
  1. Open the supplied T3 thread link.
  2. Answer the question or approval request, then use flow resume <id>.
  3. For cancellation, stop active T3 threads first.
  4. Resolve uncertain operations, then use flow cancel <id>.
Preserve the recovery records. Do not delete .flow/ to restart a job. Do not share it between hosts.

Verification boundary

Verified

  • Deterministic workflow tests with fake execution.
  • Real Git commits and pushes to a disposable local remote.
  • Lost-response recovery without duplicate publication.
  • Live T3 worktree creation and independent reviewer binding.

Not yet verified end to end

  • External T3 OAuth login through flow.
  • Live Claude drafting; the local CLI is not signed in.
  • A complete production run that creates a real GitHub PR.

No real PRs were created during implementation testing.

Agents and repository scripts must be trusted. Read-only review instructions are not an operating-system sandbox. Avoid concurrent manual worktree edits.
